# Zombieland 1.6 Test Coverage Matrix

This file defines the test surface for the RimWorld 1.6 port from the mod code outward. It is not a work log. Update it only when a test surface is added, removed, merged, or proven covered by durable evidence. Detailed scenario definitions live in `TEST_SCENARIOS.md`.

## Method

Use three axes for every test:

1. Code surface: source files, defs, Harmony targets, components, jobs, and player UI touched by the behavior.
2. Player behavior: what a real colony player can observe or break.
3. Evidence tier: source/decompiler reasoning, bridge contract, scenario save, visual/log evidence, save-load persistence, or performance smoke.

Prefer reusable scenario fixtures over one-off bridge tools. Existing bridge contracts are evidence for narrow behavior, but they do not automatically prove player-facing flows, multi-system interactions, save-load behavior, or visual quality.

Current operating order:

1. Run the static/decompiler pass first. For every Harmony patch group, confirm the target still exists, the signature still matches, closure/delegate targets still have the same role, and the patch still makes semantic sense in RimWorld 1.6 before spending live-game time.
2. Use generic bridge primitives second: spawn thing, spawn pawn, set contamination/state, select, hover, run ticks or wait for bounded semantic changes, save, load, list logs, screenshot, and read semantic state.
3. Add or keep custom bridge contracts only when they become reusable evidence for a named matrix row or scenario cluster. Delete one-off hunch probes or fold them back into generic helpers once they have served their purpose.
4. Prefer scenario fixtures over microscopic contract sprawl. Narrow contracts can isolate a defect, but combined save-load fixtures should prove that related behaviors coexist.
5. Treat logs and screenshots as first-class evidence. For UI, rendering, quests, save-load, and native crashes, a clean warning-or-higher log pass is part of the regression signal.
6. End each session with a hard boundary: build status, tests run, save names touched, files changed, temporary diagnostics removed or explicitly marked, docs updated, and the next blocker or next slice.

`coverage/ZL_COVERAGE_INDEX.tsv` is an advisory coverage ledger for planning and de-duplication. Do not interrupt an active named scenario solely because the index ranks another row highly; finish or explicitly park the current scenario with a hard boundary first.

Current local stop rule: when `coverage/COVERAGE_COMPLETENESS_REPORT.md` says the local coverage closure checkpoint is current, do not invent another baseline runtime pass merely to keep the goal moving. First rerun `scripts/coverage-inventory.sh --actionable-gates`, `--bridge-next`, `--weak-evidence-summary`, and `--consistency-checks`. If they still show no local-action backlog, make progress only by correcting stale tracking text, by reacting to changed source/dependencies, by using real newly available DLC/optional mod content, or by adding a named player-facing regression/compatibility scenario. Dependency-gated rows are not failures of the current local run.

Final DLC stretch, started 2026-06-01: the current live scope is Harmony, Core, Royalty, Ideology, Biotech, Anomaly, Odyssey, Zombieland, and RimBridgeServer. Use this phase to close only content-driven DLC evidence gaps exposed by that loadout. DLCs supply XML/defs/content and activate existing RimWorld 1.6 code paths; they do not change the game assembly. Treat DLCs as a content/input expansion, not a new baseline code version: do not rerun a covered test merely because DLCs are active unless DLC content changes the defs, pawns, jobs, thoughts, terrain, buildings, products, or map conditions used by that scenario. Therefore, do not reopen optional-mod compatibility, old CE/HAR/SoS2/RimConnect/Vehicle/Dubs/Camera+ rows, broad Core baseline scenarios, or every previously covered scenario in this pass unless the DLC loadout itself shows a regression. The right runtime shape is: identify a DLC def/content surface, spawn or exercise that content through existing generic bridge primitives or a reusable scenario contract, then record evidence only for the branch that was previously unreachable. The first runtime gate for this phase is a clean fresh process: zero mod-configuration issues, no restart mismatch, and no warning-or-higher logs before starting scenario work.

## Evidence Tiers

| Tier | Meaning | Use when |
| --- | --- | --- |
| Source | Current Zombieland and RimWorld 1.6 code prove the target shape and expected branch behavior. | Patch target signatures, branch gates, serializer formats, settings calculations. |
| Contract | A focused RimBridge/Zombieland tool verifies a narrow behavior. | Pure rules, small deterministic fixtures, regression guards. |
| Scenario | A named save plus generic setup/step/read operations verifies a player-facing flow. | Multi-system behavior, job flows, incidents, map state, save-load, settings effects. |
| Visual | Screenshot or render-state evidence verifies what a player sees. | Pawn rendering, overlays, UI, motes, projectiles, gas/effects. |
| Log | Deduped RimWorld log proves no new load/runtime errors during the scenario. | Cold start, save load, incident waves, dense tests. |
| Performance | A bounded dense-map smoke measures tick/frame cost or allocation-sensitive behavior. | Zombie tick loops, pathing, chainsaw, contamination propagation. |
